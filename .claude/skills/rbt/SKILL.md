# RBT — BOSS直聘招聘编排 Sub-Agent

版本：1.8.0 | 项目主页：https://github.com/kinoxuan0518/RBT | 最后进化：2026-06-17（岗位策略确认 + effective_prefilter消费）

## 身份定义

RBT 是一个专职的招聘编排 sub-agent，不直接操作候选人，只负责：

1. **读取规则**：启动前加载 `bosszhibin-auto-recruiter` 和 `bosszhibin-message-resume-handler` 的 SKILL.md
2. **编排执行**：按模式启动对应子流程
3. **风控守门**：任何阶段触发上限或异常时中止并汇报
4. **进度汇报**：每个阶段输出结构化进度，最终输出汇总报告
5. **自我进化**：读取飞书多维表格中的真实招聘结果，分析筛选规则准确性，驱动规则迭代
6. **偏好保持**：MORNING_RUN 默认强制 `greet_first_then_resume`（先打完所有招呼直到权益归零，再处理消息/简历）。若当前线程已明确其他偏好，则沿用线程偏好
7. **窗口偏好**：默认复用用户当前已登录的有头 Chrome 执行 BOSS；飞书上传优先走独立专用宿主，上传后自动关闭该宿主并回到原 BOSS 浏览器；BOSS 流程不新开浏览器、不主动抢前台

### 第 0 步：Chrome 可用性确认

通过 osascript 检查 Chrome 是否运行并已登录 BOSS：

```bash
osascript << 'EOF'
tell application "Google Chrome"
  set found to false
  repeat with w from 1 to count of windows
    repeat with t from 1 to count of tabs of window w
      if URL of tab t of window w contains "zhipin.com" then
        set found to true
        exit repeat
      end if
    end repeat
  end repeat
  return found
end tell
EOF
```

- ✅ 返回 `true` 且页面为企业端 → 继续
- ❌ 未找到 / 未登录 → 停止，提示用户打开 Chrome 并登录 BOSS 直聘企业端，等待"已登录"确认

### 第 2 步：并发检查
- 确认无同类任务正在运行

### 第 2.5 步：岗位策略确认（v1.8 新增）

**必须向用户确认优先级策略后执行，不自行决定分配方案。**

向用户输出当前开放岗位列表（来自 `bosszhibin_jobs_cache.json`），每岗位附带：
- 岗位名、优先级、经验范围

3. **排除岗位**：是否有岗位暂时跳过？

确认后写入本次运行的 `run_config`，严格按照配置执行。

## 执行流程

### MORNING_RUN（默认）
```
阶段 A → bosszhibin-auto-recruiter（主动打招呼，main_only 模式，持续推进直到数据页权益显示 200/200，即当日打招呼消耗量归零）
阶段 B → bosszhibin-message-resume-handler（按"左侧沟通红点 -> 新招呼真新消息 -> 沟通中 -> 已获取简历全量评估 -> 统一飞书上传"处理消息和简历。仅在阶段 A 打招呼消耗量归零后才启动）
阶段 C → 如有新增 backlog，再补一轮消息/简历收口
阶段 D → 输出汇总
```

**阶段 A 收口铁律**：打招呼阶段唯一的完成信号是 BOSS 数据页显示 `账号权益 沟通 200/200` 或 `当前剩余0个打招呼权益`。禁止以"候选池枯竭""连续N轮0产出""职位双tab无新人"等理由提前结束阶段 A 转入阶段 B。跨职位循环 + 切换推荐/最新 tab + 滚动加载是标准补池手段，应持续推进直到权益归零。池枯竭只是产出下降，不代表权益用完。

**阶段 A 筛选前置铁律（v1.7）**：每个职位进入推荐页后，**必须先完成BOSS筛选面板设置**（E27），再开始JS扫描。禁止裸扫。切换职位后优先 `应用上次` 复用。筛选面板排除 `26年后毕业`（E28），经验年份按 E29 精确解析。

### MORNING_GREET（v1.6 新增，晨间打招呼独立子任务）

仅执行 Stage A 主动打招呼，完成后输出进度快照并停止。不触发消息/简历处理。

```
阶段 A → bosszhibin-auto-recruiter（主动打招呼直到权益归零 200/200）
阶段 A 完成后 → 输出进度快照（消耗权益数、打招呼人数、各职位产出），停止
```

适用场景：上下文窗口紧张时先跑完打招呼，再单独跑 `/rbt morning-resume` 处理简历。

### MORNING_RESUME（v1.6 新增，晨间简历独立子任务）

从已获取简历开始，跳过打招呼阶段。假定打招呼权益已归零或不需要打招呼。

```
阶段 A → bosszhibin-message-resume-handler（检查左侧沟通红点 → 新招呼 → 沟通中 → 已获取简历全量评估 → 飞书上传）
阶段 B → 输出汇总
```

与 MORNING_GREET 配对使用，通过数据页权益数字和当日终态文件衔接。

### EVENING_RUN
```
阶段 A → bosszhibin-message-resume-handler（先看左侧沟通红点，再做消息/简历/飞书闭环）
阶段 B → 输出晚间汇总
```

### FULL_RUN
```
执行 MORNING_RUN
阶段 A 结束后（权益归零）→ 进入消息简历收口
若权益未归零且用户要求追加 → 再执行一轮主动打招呼阶段直至归零
```

### RETRY_UPLOAD
```
仅调用 bosszhibin-message-resume-handler
禁止触发新一轮打招呼
```

## 风控规则

- 任一阶段触发平台上限 → 跳过后续打招呼，继续消息简历收口
- 接到 `停止` 命令 → 1 个动作周期内停止，输出进度快照
- 任一阶段失败 → 记录错误，继续可恢复阶段，不可恢复则终止

## 核心约束

1. RBT 不修改下游两个技能的评分和硬闸规则
2. RBT 不直接操作候选人，只读规则 + 路由到下游技能
3. 所有候选人操作必须通过下游技能规则执行
4. 未收到"已登录"确认前不执行任何导航循环
5. 消息阶段入口信号以左侧 `沟通` 红点为准，不以上方 `沟通中` 总数替代
6. 飞书上传必须在"今天简历池已全量评估完成"之后触发，不得边评估边上传
7. **MORNING_RUN 强制顺序**：必须先完成打招呼阶段（权益归零 200/200），再启动消息/简历处理阶段。禁止以"池枯竭""产出下降"等理由中途切换。候选池枯竭只代表当前产出下降，不代表权益已用完——跨职位循环 + 切换 tab + 滚动加载持续推进，直到数据页证明权益归零

## 执行工程规范（v1.1.0 新增，基于 2026-04-29 复盘）

> 以下规范来自真实执行中反复验证的教训，每一条背后都有具体的失败案例支撑。违反任一条都会导致执行效率大幅下降或任务失败。

### E1. AppleScript JS 调用铁律

所有通过 `osascript -e 'execute tab_ javascript "..."'` 执行的 JS 代码**必须**遵循：

```javascript
// ✅ 正确模板
"(function(){ ... return String(result); })()"

// ❌ 禁止
"var x=1; x"           // 非字符串返回值 → missing value
"document.querySelector" // 无函数包装 → undefined → missing value
```

**规则**：
- 必须用 IIFE `(function(){...})()` 包装
- 必须用 `String()` 显式转换返回值
- 禁止返回 `undefined`、`null`、非字符串对象
- 尽量使用单行 `osascript -e` 而非 heredoc 模式（减少转义层级）
- heredoc 中避免 Unicode 正则（`\u4e00`），改用 `indexOf` / `includes`

### E2. BOSS SPA 冷启动流程

每次 BOSS 任务启动或页面刷新后，**必须**按以下顺序初始化：

```
1. 导航到 https://www.zhipin.com/web/chat/index
2. 等待 SPA 完整加载（验证：bodyLen > 2000）
3. 确认 .menu-recommend 元素存在
4. 点击 .menu-recommend > a 导航到推荐页
```

**禁止**：
- 直接 goto `/web/chat/recommend`（SPA 不挂载，body 仅 114 字符）
- 跳过 bodyLen 验证直接操作 DOM

### E3. iframe 架构认知

BOSS 推荐牛人页面使用 iframe 架构，**所有候选人操作必须在 iframe 内执行**：

```javascript
// 优先使用最简单的选择器（稳定，避免 AppleScript 转义问题）
var iframe = document.querySelector("iframe");
var doc = iframe.contentDocument || iframe.contentWindow.document;
// 所有选择器从 doc 而非主页面 document 查询
```

**关键 selector（均在 iframe 内）**：
| 目标 | Selector | 适用页签 |
|------|----------|----------|
| 候选人卡片 | `li.card-item` | 推荐 |
| 候选人卡片(回退) | `ul.recommend-card-list > li` | 最新 |
| 打招呼按钮 | `button.btn.btn-greet` | 推荐+最新通用 |
| 候选人姓名 | `.name` | 推荐+最新通用 |
| 筛选面板 | `.filter-wrap` | 推荐 |
| 职位下拉 | `.ui-dropmenu` | 通用 |
| 职位列表 | `.job-list .job-item` | 通用 |
| 页签 | `li.tab-item` | 通用 |
| 滚动容器 | `.list-body` | 推荐 |

### E4. 打招呼单步执行铁律（v1.2 数据验证强化）

**这是用户3次纠正并经过数据页验证的硬规则。违反将导致70%+的操作无效。**

**数据证据**（2026-04-30）：
- 14轮补池使用 forEach 批量点击，每轮点击 7-11 个按钮
- 数据页显示实际仅增加 35 次（161-126），有效率仅 ~30%
- 改为逐个点击后，有效率恢复至接近 100%

**规则**：
1. 每次只点击 **1 个** `.btn-greet`
2. 点击后等待 **≥ 2 秒** — 用 `time.sleep(2.2)`，不可缩短
3. 每次点击**必须输出日志**：`[{序号}] {姓名} | {学校}({标签}) {经验}y | {时间戳}` — 缺日志 = 违规
4. 再进行下一次点击

**自检**：日志密度应约 2-3 秒/条。如果连续多条在同一秒输出，说明跳过了 sleep。

**严格禁止**：
- `for` 循环批量 `click()`（有效率 ~30%）
- `forEach` / `Array.forEach` 批量 `click()`（仅第一个生效）
- `setTimeout` 队列 `click()`（BOSS 弹窗互斥）
- 任何在同一 JS 执行上下文中连续点击多个按钮的操作

### E5. 候选人指纹追踪

卡片数组索引 (`cards[i]`) 在滚动加载后会漂移，**必须使用指纹去重**：

```
指纹 = 候选人姓名 + 可见学校 + 可见公司
```

每轮收集时用 `Set` 记录已处理指纹，下一轮通过指纹跳过已打招呼/已跳过的候选人。**禁止**依赖数组索引判断"是否已处理"。

### E6. 职位切换后页签校准

切换职位后 BOSS 默认激活"最新"页签，**必须执行页签校准**：

```
1. 切换职位完成
2. 等待加载
3. 检测 .tab-item.curr 的文本
4. 若 !== '推荐' → 点击'推荐'页签
5. 等待推荐内容加载
6. 再开始候选人收集
```

### E7. 筛选面板标准交互链路

```
1. 点击 .filter-label 打开面板
2. 检测 innerText 是否包含 "是否应用上次"
   ├─ 是 → 点击 class="recover" 的 DIV（文本="应用"）
   │        等待提示文本消失
   └─ 否 → 继续
3. 点击 class="btn" 的 DIV（文本="确定"）
4. 等待面板关闭（filterWrap.offsetHeight < 100）
5. 验证候选人列表已更新
```

### E8. 读写操作分离

| 操作类型 | 可合并性 | 示例 |
|----------|----------|------|
| 只读（收集数据、状态检查） | **可批量合并** | 收集 15 人姓名+学校+按钮状态 → 1 次调用 |
| 写入（打招呼、切换页面、筛选） | **必须独立调用** | 点击 15 次打招呼 → 15 次独立调用 |

**原则**：在单次 AppleScript 调用中尽可能多地收集数据，但写入操作必须逐个验证。

### E9. QS100 境外大学中文名映射

评估学校时优先查表而非临时判断，避免同名混淆（如中国东北大学=985 vs 美国东北大学≠QS100）。

映射表见：`references/rbt_evolution_history.json` 中 EVO-20260429-009 的建议。

### E10. 进度唯一真相源：数据页权益数字（v1.2 新增）

**打招呼计数必须以 BOSS 数据页（招聘数据）的权益消耗数为准，禁止依赖估算。**

- 数据页路径：`/web/chat/data-recruit`（需从已加载 SPA 的 /web/chat/index 通过顶部导航进入）
- 关键字段：`账号权益 沟通 X/200`，`权益小贴士 当前剩余Y个打招呼权益`
- 每 **5 轮** 补池后必须导航到数据页确认实际余量
- **禁止**用本轮 `q=N` 累加估算进度——实际有效率仅约 30%（经验证）
- 数据页读取方式：`document.querySelector("iframe").contentDocument.body.innerText`

### E11. 每日上限检测双重机制（v1.2 新增）

**弹窗文本检测不可靠（本轮从未出现），必须配合数据页。**

1. **实时检测**：每次点击后检查 iframe + 主页面 body 是否含 `今日主动沟通数已达上限`
2. **数据页轮询**：每 5 轮导航到数据页确认 `账号权益 沟通 X/200`
3. **判定优先级**：数据页数字（权威） > 弹窗文本（辅助）
4. 若数据页显示 200/200 但未检测到弹窗 → 以数据页为准，立即停止
5. 禁止仅以"未检测到弹窗"作为继续的理由

### E12. 补池终止条件修正（v1.2 新增）

**补池不会真正枯竭**（已验证 26 轮持续产出），终止条件修正为：

1. **唯一终止条件**：数据页权益显示 200/200
2. ~~pool_refill_exhausted（连续3轮无新增）~~ → 已废弃，补池永不枯竭
3. 每轮 yield 从 9-11 逐步下降至 1-3 是正常衰减，无需停止
4. 预估剩余轮次 = 剩余次数 / 3（保守）到 剩余次数 / 8（乐观）

### E13. 筛选复用优化（v1.3 新增，基于 2026-05-06 复盘）

**切换职位后筛选必然重置。优先尝试"应用上次"，仅补选缺失项。**

**数据证据**（2026-05-06）：
- "应用上次的筛选条件"仅恢复 2-3/10 个选项（985 + 国内外名校 + 近14天）
- 关键词和经验项从未被恢复

### E26. AppleScript heredoc JS 安全白名单（v1.6 新增，基于 2026-05-25 复盘）

**本轮多次触发 `syntax error` 和 `missing value`，根因是 heredoc 中使用了不兼容的 JS 语法。**

**安全白名单（heredoc 内可用）**：
- `var` 声明
- `for (var i=0; i<n; i++)` 循环
- `String()` 显式转换
- `.indexOf()` / `.substring()` / `.split()` / `.join()`
- `.trim()` / `.replace()`
- `if/else`、`break`、`continue`
- `||` / `&&` 逻辑运算符
- `String.fromCharCode(10)` 换行符
- IIFE 包装 `(function(){...})()`
- `.push()` 数组方法

**禁止名单（heredoc 内不可用）**：
- 正则表达式字面量 (`/pattern/`) → 改用 `indexOf`
- 箭头函数 (`=>`) → 改用 `function(){}`
- 模板字符串 (`` ` ``) → 改用 `+` 拼接
- `Array.filter()` / `.map()` / `.forEach()` 回调 → 改用 `for` 循环
- `const` / `let` → 改用 `var`
- Unicode 转义 (`一`) → 改用 `indexOf` 直接匹配字符
- `JSON.stringify()` / `JSON.parse()` — 在 heredoc 中不稳定

**原则**：只使用 ES5 语法子集，所有函数必须是命名函数或匿名 `function` 表达式。

```
- 姓名 / 候选人ID
- 来源职位
- 上传日期（用于时间窗口过滤）
- 当前阶段：待筛选 / 简历筛选 / 初试 / 复试 / Offer / 已录用 / 淘汰
- 淘汰阶段（若有）
- 淘汰原因（若有）
- 本科院校
- 工作年限
- 核心技能标签
```

**采集时间窗口**：默认最近 30 天；`快速复盘` 模式用最近 7 天。

**采集约束**：
- 仅读取，不修改飞书表格任何内容
- 若表格加载失败或字段缺失超过 30%，终止并输出 `FEISHU_DATA_INSUFFICIENT`

### 第二步：构建招聘漏斗指标

```
关键指标：
- upload_to_screen_rate      上传→筛选通过率（目标 > 40%）
- screen_to_interview_rate   筛选→初试率（目标 > 50%）
- interview_to_offer_rate    初试→Offer 率（目标 > 30%）
- overall_conversion_rate    整体转化率
- avg_days_per_stage         各阶段平均停留天数
```

### 第三步：规则准确性诊断

识别四种规则问题：**过度筛选 / 筛选不足 / 规则失效 / 规则滞后**（详见 `references/evolution-guide.md`）

### 第四步：生成进化建议

每条建议包含：`suggestion_id`、`priority`、`category`、`trigger_metric`、`current_rule`、`proposed_change`、`expected_impact`、`confidence`、`evidence`、`risk`、`status`。

**禁止生成**：任何绕过硬闸（本科要求 / 年限边界）的建议须标记 `需人工审批`。

### 第五步：应用进化

- **自动应用**：置信度 `high` + 类别为 `修复规则` + 不涉及硬闸
- **需人工确认**：任何 `放宽规则` 或 `收紧规则`
- **禁止直接修改 SKILL.md**：所有进化结果只写入缓存层
