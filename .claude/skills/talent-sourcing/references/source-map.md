# Source Map

用于告诉 `talent-sourcing` 在不同任务下优先看哪些 source，而不是一上来全网乱搜。

## 1. 常规渠道寻人

适用：

- 标准岗位招聘
- 需要稳定批量召回
- 后续要进入招聘渠道触达

优先 source：

- 脉脉
- LinkedIn
- BOSS / 其他招聘平台

辅助验证：

- GitHub
- Hugging Face
- Google Scholar / arXiv

## 2. 冰山以下人才挖掘

适用：

- 平台上不活跃
- 不一定在招聘平台留痕
- 更偏研究、开源、项目或团队核心贡献

优先 source：

- GitHub
- Google Scholar
- arXiv
- Hugging Face
- 个人主页 / 博客
- 项目主页 / contributor 页面
- 实验室主页 / 公司团队页

输出重点：

- 这个人为什么会被认为属于目标画像
- 证据来自哪个 source
- 适合后续通过什么渠道触达

## 3. 指定人物调研

适用：

- “这个人值不值得挖”
- “Peak 这种人怎么找”
- “帮我研究某个人是不是做这个方向”

优先 source：

- LinkedIn
- GitHub
- Google Scholar / arXiv
- 公开网页搜索
- 项目页 / 团队页

必须回答：

- 身份是否能被交叉验证
- 方向是否真的匹配
- 是硬证据还是推断
- 是否值得进入触达流程

## 4. Builder / Operator 型人才映射

适用：

- “找 Peak 这种人”
- “找 Cat Wu / Peter Steinberger 这类人”
- 想找既懂技术又能把 AI 产品做出来的 builder

优先 source：

- LinkedIn
- GitHub
- 公司 team page
- 产品发布页 / launch page / changelog
- 个人博客 / 访谈 / conference page

输出重点：

- 这类人的共同 archetype 是什么
- 哪些是产品或项目硬证据
- 哪些公司/项目是这类人的高密度来源
- 下一步更适合从哪个渠道继续扩展或触达

## 5. Source 使用原则

- LinkedIn：职业身份最强，但方向深度证据可能不足
- GitHub：工程和开源证据最强，但不是所有优秀人才都公开活跃
- Scholar / arXiv：研究证据强，但需要防止“作者挂名”或“研究不等于工程能力”
- Hugging Face：适合模型、数据、benchmark 和应用型证据
- 脉脉：适合中文职业身份和后续执行触达
- 飞书历史数据：适合去重、优先级和反馈闭环，不适合做外部召回主源
- 公司 team page / 产品发布页 / 访谈页：特别适合 builder-operator 类型人才，因为这类人常通过“作品”和“角色”留下公开证据
